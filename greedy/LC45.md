### 二刷 (8/5/2026) ❌ 没思路

**卡在哪**：知道「到达某个节点就要起跳」，但分不清 `curDistance` 和 `nextDistance` 该怎么配合。一度以为只有 `curDistance >= n-1` 才是对的 break 条件，觉得用 `nextDistance` 判断像是提前用了一个还没生效的值。

**真正的坎**：没建立「分层」模型。这题本质是 BFS——`curDistance` 是当前层右边界，`nextDistance` 是扫描当前层时顺手算出的下一层右边界。`i == curDistance` 触发的不是「起跳」这个动作，而是「这一层扫完了，可以决定跳」。

> **自检信号**：纠结「这一步该维护几个 variable」时，先问「这是第几层」——分层想清楚了，variable 该放哪就明确了。

### 三刷 (8/6/2026) ⚠️手生 一次写对，口答半通

分层骨架落地了：`nextDistance` 每轮无条件更新（没塞进 if）、`curDistance` 只在 `i == curDistance` 那一刻跳变、`n == 1` 的 early return 也在。

**loop 上界写成了 `i < nums.length`**（标准写法是 `nums.length - 1`，最后一格不进 loop）。**能对，但脆**：它靠的是 break 先生效——`curDistance` 一旦覆盖末端就当场退出，所以 `i == curDistance == n-1` 这个会多算一次 `count++` 的组合永远走不到。正确性隐式耦合在相隔几行的 break 上。

和 **LC55 二刷是同一行**：那次 `i < nums.length` 把可达性检查整个丢了（错的），这次是「对但脆」。这一行是这两题的共同压力点。

自测点①答出（数值上刚赋完值相等 → 判谁都一样；语义上选 `nextDistance` 因为它代表「下一跳能到多远」）。②只答到「当前这一跳能走到头了，下一跳计数」，没收到「**决定跳** vs 正在跳」这条线上——该自测点已讲透，作废。

### 四刷 (8/10/2026) ❌ 把「跳数」当成「层边界」去比，三刷已落地的骨架没留住

```java
class Solution {
    public int jump(int[] nums) {
        int cur = nums[0];      // ❌② 初值宣称"第一跳已跳过"，但 count=0 说的是"一次没跳"
        int next = 0;
        int count = 0;
        if(nums.length == 1) return 0;
        for(int i = 0; i < nums.length; i++){
            next = Math.max(next, i + nums[i]);   // ✅ 三刷的骨架还在，无条件更新
            if(i == count){
                // ❌❌① 核心错误：应为 i == cur。count 是"跳了几次"，
                //      cur 是"当前层右边界"，两个完全不同的量
                count++;
                cur = next;
                if(next >= nums.length - 1) break;
            }
        }
        return count;
    }
}
```

**①的根因**：`count` 和 `cur` 都从 0 附近开始增长，所以前几个 test case 蒙对了。真正的信号是——**`cur` 现在只被写、从不被读**（`cur = next` 之后没有任何地方用它）。这是 LC274 那条自检信号的镜像版：274 是「声明了却从未被读取」，这次是「赋值了却从未被读取」。同一个意思：**写进去没人用，说明它本该承担的角色被别的东西顶替了**——顺着 `cur` 找就能找到出错那一行。

**加特判是信号不是修复**：补上 `nums.length == 1` 后 test case 从 39 涨到 44，多过的全是长度 1 的 case，真 bug 一个没动。**特判能提高通过率，通常说明主逻辑有洞**（同 LC55 三刷 ❌③）。

**②**：`cur` 初值应为 `0`。一步没跳时你就站在下标 0，右边界是 0；`nums[0]` 是跳完第一次之后的边界。写 `nums[0]` 等于宣称第一跳已发生，而 `count = 0` 宣称一次没跳 → 第一跳不被计数，最终少 1。改成 0 后 i=0 那轮自然算出第 1 层，不用手喂初值。（`nums.length == 1` 的特判仍要留，与初值无关：n=1 时 i=0 那轮会先 `count++` 再 break，返回 1，而正确答案是 0。）

> **初值必须讲同一个故事**——第三次出现（LC80 二刷、LC55 三刷）。**自检**：写完初始化那几行，问「如果 loop 一轮都不跑，这些值合起来描述的是什么状态？」答案应该是「什么都没发生」。

**自测点口答**：两问最终都答出——`next` 在 if 外是因为要在整个可达范围里逐格维护最大值；挪进 if 则只在层的最右端算一次 max，退化成 `cur = cur + nums[cur]`，中间跳得远的格子全看不见。表述散在两条消息里、次序倒着来（先讲 `cur = next` 再回头补 `next` 的位置），属**口答手生**，不是卡推导。

> **退化的反例**：`[2,3,1,1,4]`——正确解 i=0,1 都参与 max → next = max(2, 1+3) = 4 → 2 跳；退化解只看 i=2 那格 → cur = 3，再起跳 → 3 跳。**「最远的那一格」≠「跳得最远的那一格」**，greedy 挑的是下一跳覆盖最广的位置，它往往在层的中间。

**同轮澄清的 loop 上界问题**（她主动问「45 要不要像 55 那样写 `i <= cur`」）：可以写，但**在 45 里不承担任何责任**。55 的 `i <= cur` 是可达性的唯一检测器，循环正常结束就等于 `return false`；45 题目保证终点必达，这个哨兵永远不开火，真正终止 loop 的是 break。上界该写 `nums.length - 1`，防的是另一件事——最后一格若恰好 `i == cur` 会多算一次 `count++`。

### 核心思路（一句话）

**把数组按「跳几次能到」分层：`curDistance` 是当前层右边界，`i` 扫到边界说明这层扫完了，用扫描中攒下的 `nextDistance` 决定要不要再跳一次。**

### 代码

```java
class Solution {
    public int jump(int[] nums) {
        int curDistance = 0;       // 当前跳数能覆盖到的最远下标（这一层的右边界）
        int nextDistance = 0;      // 扫描这一层时，顺手算出的下一层最远右边界
        int count = 0;
        for (int i = 0; i < nums.length - 1; i++) {   // 最后一格不用再决定起跳
            nextDistance = Math.max(nextDistance, i + nums[i]);   // 每格都要参与 ← 关键
            if (i == curDistance) {                    // 这一层扫完了 → 决定跳 ← 关键
                count++;
                curDistance = nextDistance;
                if (curDistance >= nums.length - 1) break;   // 已能到终点，不用再扫
            }
        }
        return count;
    }
}
```

**两个 `← 关键` 是这题的全部考点**：`next` 在 if 外（否则退化成从层右端起跳）、比的是 `curDistance` 而非 `count`（四刷栽在这里）。

### 复杂度分析

**Time: O(n)**：每个下标只参与一次 `nextDistance` 更新，一次遍历。
**Space: O(1)**：三个 variable。

对比 brute force O(n²)（从每个可达位置枚举/DFS 试跳取最小）：greedy 把「选最优跳点」压缩成扫描时顺手维护的一个 max，不必真的枚举每种跳法。

### 沉淀

- **`count++` 是「决定跳」，不是「正在跳」**：不需要知道具体从这一层哪个点起跳，只要这一层扫完、知道下一层能到哪，答案就定了——代码里从不记录「从哪跳」。说岔成「正在跳」，就会觉得站在终点那格也该算一跳 → 多算。这也是 `break` 必须在 `count++` **之后**的原因：先记下「我决定跳」，再检查这一跳够不够到终点。
- **BFS 分层视角**：`curDistance` = 当前层右边界，`nextDistance` = 下一层右边界，`count` = 层数。想不清 loop 在干嘛时，回到「这是第几层」。
- **变量角色混淆是本题最贵的错**（四刷）：`count`（层数）和 `curDistance`（层边界）在脑子里是清楚的，写到 `if` 那一行时抓错了名字。症状是**某个变量只被写、不被读**——把它当固定的自检项。
- **初值必须讲同一个故事**（与 LC80 二刷、LC55 三刷同一条）：`curDistance` 和 `count` 都在说「已经跳了几次」，两者对不上就会差一跳。
- **loop 上界要能独立成立**，别靠 break 兜底：写 `nums.length - 1` 是从源头排除最后一格，正确性不依赖别的行。

### 引申：跟 LC55 的对照

- 55 只答「能不能到」，一个 `coverRange` 就够，覆盖到终点直接 `return true`。
- 45 要答「最少几步」，必须多一个 `nextDistance` 把「当前层」和「下一层」分开，否则不知道该在哪个时间点给 `count` 加一。
- **loop 上界那一行责任不同**：55 的 `i <= coverRange` 是可达性的唯一检测器，循环正常结束 = `return false`；45 题目保证必达，同样写法只是永不开火的哨兵，上界该写 `nums.length - 1` 来排除最后一格。**先分清上界在承担语义还是只防越界，再决定写什么。**

### 关联

- 55（同一坐标关系的单变量版本：55 判「能不能到」，45 判「最少几步」）
- 274（四刷 ❌❌① 与其「阈值抓错 variable」同族——变量角色在脑子里清楚、写到那一行时抓错名字）

### Interview pitch (练口述)

> "I treat this as layered BFS: curDistance is the rightmost index reachable with the current number of jumps, and while scanning that layer I track nextDistance, the farthest index reachable with one more jump. When i reaches curDistance, that layer is fully scanned, so I commit to another jump — count++ — and move the boundary to nextDistance. If that boundary already covers the last index, I stop immediately, since I've proven a jump count that reaches the end. O(n) time, O(1) space, versus brute-force DFS trying every jump sequence."
