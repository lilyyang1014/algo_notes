### 三刷 (8/21/2026) ❌ 三处错，思路在但没落地

```java
for (int i = 0; i < gas.length - 1; i++) {   // ❌③ 上界少一格，最后一站被跳过
    cur = gas[i] - cost[i];                  // ❌❌① 应为 cur += ，覆盖掉了累计
    total += gas[i] - cost[i];               //     ✅ total 这行是对的
    if (cur < 0) {
        start++;                             // ❌② 应为 start = i + 1
        cur = 0;
    }
}
```

**①（核心）**：`cur` 模拟的是**油箱**，油箱本来就有存量，必须累加。写成 `=` 之后 `cur` 只反映单站盈亏，于是 `cur < 0` 判的变成「这一站自己亏」而不是「从 start 走到这撑不住了」——**判断的含义整个变了**。单站盈亏根本不是判据：`gas=[1,2,3,4,5], cost=[3,4,5,1,2]` 里自身不亏的是 3 和 4 两站，正确起点却只有 3。

**②（我自己定位的）**：前面这一整段的油箱为负了，start 要跳到 `i+1`，不能 `++`。`start++` 是把「第几格」当成「失败了几次」在数，还丢掉了整段跳过这条剪枝，退化成 O(n²)。

**③**：绕圈问题每一站都要算，没有「最后一站不用管」。

**①②是连着的**：`cur` 一退化成单站值，重置就没了依据，`start++` 顺理成章地被写出来。

### 核心思路（一句话）

**`totalSum >= 0` 决定「有没有解」，`curSum` 转负的位置决定「解在哪」——一趟 scan 同时算这两件事。**

### 代码

```java
public int canCompleteCircuit(int[] gas, int[] cost) {
    int curSum = 0;      // 从 start 到 i 这一段的净油量（有存量，必须累加）
    int totalSum = 0;    // 全程净油量，判可行性，全程不清零
    int start = 0;
    for (int i = 0; i < gas.length; i++) {
        curSum += gas[i] - cost[i];
        totalSum += gas[i] - cost[i];
        if (curSum < 0) {
            start = i + 1;   // [start, i] 整段作废，i+1 尚未检验
            curSum = 0;      // 只清 curSum
        }
    }
    return totalSum >= 0 ? start : -1;   // == 0 有解，不能写 > 0
}
```

### 推导一：为什么整段 `[start, i]` 可以一次跳过

设 `curSum` 在 `i` 处首次转负，取段内任意 `j`：

从 start 出发能走到 j（是走到 i 才断的），说明**开到 j 时油箱里还有富余**。那从 j 自己出发呢？它起步是空的，比「从 start 开过来的那个自己」**少了那份富余**。带着富余的版本走到 i 都断了，油更少的版本只会**更早断**。

所以段内每一格做起点都必定失败 → 整段一次排除。这就是 O(n²) 压成 O(n) 的地方。

### 推导二：为什么不用验证 `start` 之后能绕回开头（四刷卡在这）

按 `start` 把整圈切两段：**A = start → 末尾**，**B = 开头 → start-1**。记 A 走完剩下 `cur`、B 整段的净油量是 `rest`，那么 `totalSum = cur + rest`。

从 `start` 出发就是先走 A 再走 B：

1. **A 段不会断**：全程 `curSum` 没再转负（否则 start 早被挪走了），走完手上有 `cur ≥ 0`。
2. **B 段总量填得平**：进 B 段时手上有 `cur` 打底，而 `totalSum ≥ 0` 就是 `cur + rest ≥ 0`——A 攒的富余够补 B 的亏空。
3. **B 段中途也不会断**：走一遍 `[1,2,3,4,5] / [3,4,5,1,2]` 看。start = 3，A 段是站 3、4，走完 `cur = 3+2-1-2 = 2`。进 B 段（站 0、1、2）时手上有 2：过站 0 变成 `2+1-3 = 0`，过站 1 变成 `0+2-4 = -2`……等等，这会断？不会——`rest = -2`，而 `cur + rest = 0 = totalSum`，中途最低点恰好是 0，不是负的。关键在于 **B 段里最亏的那一截，正是当初让 `curSum` 转负、被挪掉起点的部分**，它之后的部分只会往回赚。所以中途任何一点手上的油都 `≥ cur + rest = totalSum ≥ 0`。

> 直觉：**富余是先拿到的，亏空是后遇到的**。总量够填，顺序又保证先攒后花，所以中途不会断。

`totalSum` 已经替你验证了 B 段——这就是一趟 scan 等价于绕圈的全部理由。

### 推导三：`start` 会不会跑到 `gas.length`（五刷卡在这）

会。如果最后一格让 `curSum` 转负，`start = i + 1` 就是 `gas.length`——一个不存在的站。所以「`+1` 要想越界」这个警觉是对的，但要先分清两种 `+1`：

- **访问型**（`gas[i+1]`）：真会崩，那一格不存在。
- **赋值型**（`start = i + 1`）：不崩。`start` 只是个 int，装 `gas.length` 完全合法，这一行从头到尾没拿它去索引数组。

那为什么不加 guard 也能 AC？把两件事接起来：

最后一格让 `curSum` 转负 → **最后那一段的和是负的**。而前面每一段被丢掉时也都是负的（那正是丢它们的理由）。**所有段都是负的 → `totalSum` 不可能 ≥ 0**。

于是 `totalSum >= 0 ? start : -1` 走的是 `: -1` 那一支，那个非法的 `gas.length` 根本没机会被返回。

> **一句话**：`start == gas.length` 和 `totalSum < 0` 必然同时发生，后者把前者挡在了 return 外面。

所以那个 guard 不是冗余代码，是**防呆**——它把「靠下游几行兜住」这层隐式耦合显式化了。判冗余的通用判据（删掉它，触发条件还可能满足吗）在这里答案是「能满足，但被下游拦住了」，属于该留的那一类。

### 复杂度分析

**Time: O(n)**：单趟 scan，`start` 单调右移不回退。
**Space: O(1)**：三个 int。

对比 brute force O(n²)（枚举每个起点各模拟一圈）：省在「一整段候选一次排除」，不是逐个起点重试。

### 沉淀

- **`=` 还是 `+=`，先问「这个量有没有存量」**。凡是「前缀和跌破 0 就重开」的形态（134、53），那个变量都在模拟一个会攒的东西，必然累加。三刷栽在这。
- **一个量管存在性、另一个管构造，别互相顶替**：`totalSum` 答「有没有」、`curSum` 答「在哪」，只有后者随起点重置。拿全局量去论证局部结论（四刷）是坏味道。
- **`+1` 分两种**：访问型（`arr[i+1]`）会越界，赋值型（`start = i+1`）不会——后者只是存了个数。担心越界之前先看这个 `+1` 有没有被拿去索引。
- **`start` 是「第几格」不是「第几次」**：该被赋值成一个位置，不该被 `++`。同族：189 的 `n-k`、45 的 `i == count`、367 的 `left`/`left²`。
- **可行性判据的等号方向单独想一遍**：`totalSum == 0` 是「恰好开完」不是「差一点」。凡「总量够不够」型判断，先问 0 归哪边。
- **正确性别只靠相隔几行的那个判断兜着**：这题的 `start` 合法性是被 return 行的 `totalSum` 挡住的，改动附近代码就会咬人。同模式：LC45 靠 break、LC55 靠「cur ≥ n-1 就 return」。
- **greedy 跳跃型的通用形态**：证明「区间内每点都不优于端点」→ 整段跳过 → O(n²) 压成 O(n)。134 和 45 共用这个骨架。

### Interview pitch (练口述)

> "Brute force would try every station as a start and simulate a full loop — O(n²). The key insight is that two separate questions can be answered in one pass. First, feasibility: if total gas minus total cost is negative, no start works, since any full loop consumes that same total — and exactly zero is still feasible. Second, locating the start: I track a running sum from the current candidate. The moment it goes negative at index i, no station in that whole segment can work — any later station j in it starts without the surplus it would have had arriving from start, so it'd reach i with even less gas. I jump start to i plus one and reset only the running sum, never the total. I don't need to verify the wrap-around: the segment from start to the end finishes with a non-negative surplus, the remaining prefix is covered because total is non-negative, and the surplus is collected before the deficit is hit. One edge case worth naming: if the last station is the one that goes negative, start becomes n, which isn't a valid index — but that can only happen when every segment was negative, so total is negative too and we return minus one anyway. One pass, O(n) time, O(1) space."
