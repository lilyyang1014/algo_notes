```java
Map<String, Integer> map = new HashMap<>();      // 方案 A：map 里已含 IV/IX/.../CM 六个双字符 key
map.put("I",1); ... map.put("M",1000);

int ans = -1;                                     // ❌④ 应为 0；且 i 从 1 起 → s.charAt(0) 从头到尾没被加过
for(int i = 1; i < s.length(); i++){
   if(s.charAt(i) == "V" && s.charAt(i-1) == "I"){ // ❌① char 和 String 不能比，应为 'V'（编译错误）
    ans = 4;                                       // ❌⑤ 赋值覆盖不是修正；下面还会再加一次 → "IV" 算成 4+5
   }else if( ... 手写六对减法规则 ... ){            // 方案 B：把 map 里已有的信息又抄了一遍
    ans = 1000;                                    // ❌⑥ CM 是 900。手写那份和 map 那份不一致，而 map 是对的
   }
   if(maps.containsKey(s.charAt(i))){              // ❌② maps 未定义（编译错误）
    ans = ans + map.get(s.charAt(i));              // ❌❌③ 方案 C：拿 char 查 String 的 key，恒 false
   }
}
```

**③的根因（核心，静默）**：`Map<String, Integer>` 的 key 是 String，`s.charAt(i)` 是 char → autobox 成 `Character`，`Character` 和 `String` 永远不 equals → **`containsKey` 恒为 false，累加那一行一次都没执行**。

编译器不拦，因为 **`containsKey` / `get` / `remove` 的参数类型是 `Object` 而不是 `K`**——泛型擦除的历史包袱，你传什么它都收。**类型写错在这里是运行期静默失效，不是编译错误。** 与 `list.remove(int)` vs `remove(Object)` 那个重载坑同源（LC380）。

**为什么自己读不出来**：A（map 查表）和 B（手写规则）是同一件事的两种实现，留一个就够；C 单独配上「比右邻小就减」也能成立。三条拼起来 → B 覆盖 ans、C 又加一次、A 因 key 类型不对压根没生效。**每一半单独看都对，所以通读代码查不出问题。**

**归族**：与 LC34 8/4「调用处用三刷的 L 版、condition 用四刷的 U 版」同形——**两套各自正确的方案拼在一起**。

> **自检信号**：写完发现同一个信息在代码里存了两遍（map 里有 IV，if-chain 里又手写一遍 IV），停下——**冗余不是无害，是两份会不一致**（本题 CM 手写成 1000、map 里是 900，就是这么来的）。留一份，删另一份。

### 核心思路（一句话）

**罗马数字正常从大到小排，一旦「小的在左、大的在右」就必是六种减法组合之一——所以「比右邻小」这一个判断等价于全部六条规则，不需要枚举。**

### 方案 A：双字符 token 优先查表

```java
Map<String, Integer> map = new HashMap<>();   // 七个单字符 + 六个双字符，共 13 个 key
// I=1 IV=4 V=5 IX=9 X=10 XL=40 L=50 XC=90 C=100 CD=400 D=500 CM=900 M=1000

int ans = 0, i = 0;
while (i < s.length()) {                                    // 步长不固定，for 装不下
    if (i + 1 < s.length()                                  // guard 必须早于 substring
            && map.containsKey(s.substring(i, i + 2))) {
        ans += map.get(s.substring(i, i + 2));
        i += 2;                                             // 吃两格
    } else {
        ans += map.get(s.substring(i, i + 1));              // 别只写 i++，加数是对称的
        i++;                                                // 吃一格
    }
}
return ans;
```

**双字符必须先试**：单字符永远查得到，先问它的话双字符再没机会被问到，"IV" 会拆成 1+5=6。

### 方案 B：只存单字符，靠比大小（这题真正的解法）

```java
Map<Character, Integer> map = new HashMap<>();   // 只放 I V X L C D M 七个
int ans = 0;
for (int i = 0; i < s.length(); i++) {
    int cur = map.get(s.charAt(i));
    if (i + 1 < s.length() && cur < map.get(s.charAt(i + 1))) {
        ans -= cur;      // 比右邻小 → 它是被减的那个
    } else {
        ans += cur;
    }
}
return ans;
```

A 的六个双字符 key 是**冗余信息**（`V-I=4` 推得出来）；B 把六条规则压成了一条性质。面试首选 B，A 更好懂。

### 复杂度分析

**Time O(n)**：两版都是每格常数次 map 查询。A 的 `substring` 每次新建 String（O(1) 长度，不影响量级）。
**Space O(1)**：map 是常数大小（13 或 7 个 entry），与输入无关。

### 沉淀

- **`containsKey` / `get` / `remove` 的参数是 `Object` 不是 `K`**：类型写错编译器不拦，运行期恒 false / 恒 null。集合的**查询类**方法几乎都放宽成了 `Object`。同族 LC380 的 `list.remove(int)` vs `remove(Object)`
- **同一个信息别在代码里存两遍**：冗余的两份迟早不一致（本题 CM 手写 1000 / map 里 900）
- **两条分支的事项数必须相等**：本题每条路都要「查表加数 + 前进」两件事，只有内容不同。漏掉一件是静默错误，同 LC380 二刷「swap 只写一半」
- **规则的适用范围有包含关系时，范围窄的必须先判**：双字符优先于单字符。分支顺序本身在承担逻辑，不是随便排的
- **`substring(a, b)` 左闭右开**，返回 String（哪怕只取一格）；`charAt(i)` 返回 char。同一格取出来是两个不同类型，别混
- **步长不固定就别用 for**：for 的 update statement 写死了，`i += 2` / `i++` 二选一的场景用 while
