## 274. H-Index

Date: 8/6/2026
Difficulty: Medium
Tags: sorting, brute force optimization

![LC274 sorted ascending: citations[n-h] is the h-th largest, so counting becomes an index lookup](assets/274.png)

### 一刷 (8/6/2026) ❌ 跳过 brute force 直接写 greedy，失去了发现瓶颈的位置

```java
class Solution {
    public int hIndex(int[] citations) {
        int hIndex = 0;
        for(int i = 0; i< citations.length; i++){
            if(citations[i] > hIndex) hIndex++;
            // ❌❌① 这行 greedy 只在降序排好时成立 → 缺 Arrays.sort()
            if(citations[i] > 0) hIndex = Math.min(hIndex, citations[i]);
            // ❌② h 是单调不减的累计量，min 让它回退；`> 0` 是给补丁打的补丁
        }
        return hIndex;
    }
}
```

**①的根因**：排序后「下标 i 前面的 i+1 个 element 都 ≥ citations[i]」这个不变量成立，
count 才有意义。**模板和它的前提是一体的，前提丢了模板就是错的。**
反例 `[1,3,1]`（答案 1）：`1>0→h=1`，`3>1→h=2` ❌ 只有 1 篇 ≥2。删掉②也照样错。

**真正的根因**：没写 brute force → 没有「外层 × 内层」的式子 → 没有能指着说
「瓶颈在这」的东西 → **排序无处可推**。它不是灵光一现，是观察瓶颈的必然结果。

**自测点**：不看答案说出 brute force 是「什么 × 什么」，以及为什么该砍内层而不是外层

### 第一步：定义翻译成可判定的谓词

题意「至少 h 篇论文，每篇被引用至少 h 次」→

```
valid(h) ⟺ 引用数 ≥ h 的篇数 ≥ h
答案 = 最大的成立的 h
```

**先把「答案是什么」写成能对任意候选判真假的式子**，后面所有决策从它长出来。
一刷跳过的就是这一步。

### 第二步：brute force

h 的范围是 `[0, n]`（h 篇不可能超过总篇数），挨个试：

```java
for (int h = 0; h <= n; h++) {      // 闭区间 → <=
    int count = 0;                  // 声明在循环体内 = 自动重置
    for (int c : citations) {
        if (c >= h) count++;        // "至少 h 次" → 带等号
    }
    if (count >= h) ans = h;        // 从小往大试，后面覆盖前面
}
```

### 第三步：写出瓶颈的乘法式

```
外层：h 从 0 到 n     → n+1 次
内层：扫一遍数组数数   → 每次 O(n)
总代价 = (n+1) × n ≈ O(n²)
```

**嵌套循环的优化只有三个方向**：① 外层跑得少 ② 内层变便宜 ③ 换角度。
没有第四个。逐个乘数看能不能砍，这就是分析的全部动作。

### 第四步：为什么选砍内层

**先看内层在干什么**——判断它的性质，只有三类：

| 内层在干嘛                                 | 能砍吗      | 工具                           |
| ------------------------------------------ | ----------- | ------------------------------ |
| 在找 / 在数                                | ✅ 几乎总能 | HashMap、排序、前缀和          |
| 在算区间和 / 最值                          | ✅ 能       | 前缀和、单调栈、sliding window |
| 真正必要的独立计算（各轮无可复用中间结果） | ❌ 砍不动   | —                              |

判断的核心问题：**各轮之间有没有重复劳动？**

本题内层是「数有多少个 element ≥ h」——h=3 时数一遍，h=4 时**扫的还是同一个数组**。
大量重复 → 可以预处理 → **砍得动**。

**再看外层能不能砍**——条件是谓词单调（真真真假假假，只有一个跳变点）。
当场验证的方法是问一句：**「h 成立，h-1 一定也成立吗？」**

> h=3 成立说明有 3 篇引用 ≥3；这 3 篇既然 ≥3 就一定 ≥2，所以至少 3 篇 ≥2，够 2 篇 → 一定成立 ✅

单调成立，所以**外层也砍得动**（二分答案，n+1 次 → log n 次）。

**两个都能砍，为什么选内层？** 算总账：

| 砍哪个                     | 外层  | 内层 | Time           |
| -------------------------- | ----- | ---- | -------------- |
| 砍外层（二分答案，不排序） | log n | O(n) | O(n log n)     |
| **砍内层（排序）**         | n     | O(1) | **O(n log n)** |

打平。这时候选内层的理由是**工程性的**：二分答案要自己写 lo/hi/mid 的收缩逻辑，
边界容易错；排序是一行库函数，写完剩下的是一个平凡的单层遍历。
**代价相同时选出错面小的那个。**

> 顺带：**两个别一起上**。排完序再二分是白搭——排序已经付了 O(n log n)，
> 再省下遍历的那 O(n) 不改变总账，只增加出错机会。
> **砍到瓶颈不在那儿了，就该停手。**

### 第五步：砍内层 —— 把「数一遍」变成「查下标」

升序排好后，下标 `n-h` 上的就是第 h 大，它前面（含自己）恰好 h 个都 ≥ 它。
「有多少个 ≥ h」从要数变成一次查表。

```java
class Solution {
    public int hIndex(int[] citations) {
        Arrays.sort(citations);                              // 升序 [0,1,3,5,6]
        int h = 0;
        for (int i = citations.length - 1; i >= 0; i--) {    // 倒序 = 从大到小
            if (citations[i] > h) h++;                       // 够格 → 推进一格
            else break;                                      // 后面只会更小
        }
        return h;
    }
}
```

```
i=4  c=6   6>0 ✅ h=1        i=1  c=1   1>3 ❌ break
i=3  c=5   5>1 ✅ h=2        return 3
i=2  c=3   3>2 ✅ h=3
```

**验证砍对了地方**：内层那个 `for (int c : citations)` 已经不见了，被 `citations[i]` 顶替。
这就是分辨砍了哪个乘数的方法——**内层的 for 还在不在**。

### 复杂度分析

**Time: O(n log n)**：`Arrays.sort` 主导；之后单层遍历 O(n)，被排序盖住。
**Space: O(1)**：int[] 用 dual-pivot quicksort，in-place。

对比 brute force O(n²)：快在把「每个候选都重新数一遍」换成「排一次序，之后全部 O(1) 查」。
**预处理一次，代替反复现算——这是砍内层的通用形态。**

### 沉淀：拿到暴力解之后的固定动作

1. **写出「外层次数 × 内层代价」**。没有这个式子就没有优化可谈，
   一刷的全部问题就在这里
2. **先看内层**：它在「找 / 数 / 求区间和」吗？各轮之间有重复劳动吗？
   有 → 砍得动，用预处理（排序 / HashMap / 前缀和）换掉它
3. **内层砍不动再看外层**：问「h 成立 ⟹ h-1 一定成立吗」，答不出"一定"就免谈二分
4. **两个都能砍时算总账**，打平就选出错面小的
5. **砍完一个就停**，别叠加

**为什么优先看内层**：内层是被外层放大的那个乘数，而且"重复劳动"这件事一眼能看出来，
比验证单调性省脑子。

### 沉淀：等号边界（本次两个 mechanical error 同族）

| 错误写法 | 漏掉       | 反例             | 正确     |
| -------- | ---------- | ---------------- | -------- |
| `h < n`  | h = n      | `[1]` → 返回 0   | `h <= n` |
| `c > h`  | c 恰好 = h | `[1,1]` → 返回 0 | `c >= h` |

第一处尤其刺眼：**注释里写了 `[0,n]`，代码里写成 `< n`**——和二分「边界更新那一行」
同族，推导在脑子里没接到代码上。

> **自检信号**：每写一个比较符号问一句「相等时算不算」。中文的「至少 / 不少于 /
> 不超过」直接对应带等号的比较符。本题三个符号全带等号，因为定义里全是「至少」。
