## 274. H-Index

### 一刷 (8/6/2026) ❌ 跳过 brute force 直接写 greedy，失去了发现瓶颈的位置

```java
class Solution {
    public int hIndex(int[] citations) {
        int hIndex = 0;
        for(int i = 0; i < citations.length; i++){
            if(citations[i] > hIndex) hIndex++;
            // ❌❌① 核心错误：这行 greedy 只在排好序时成立 → 缺 Arrays.sort()
            if(citations[i] > 0) hIndex = Math.min(hIndex, citations[i]);
            // ❌② h 是单调不减的累计量，min 让它回退；`> 0` 是给补丁打的补丁
        }
        return hIndex;
    }
}
```

**①的根因**：排序后「下标 i 之前的 i+1 个 element 都 ≥ citations[i]」这个 invariant 成立，count 才有意义。**模板和它的前提是一体的，前提丢了模板就是错的。** 反例 `[1,3,1]`（答案 1）：`1>0→h=1`，`3>1→h=2` ❌ 只有 1 篇 ≥2。

**真正的根因**：没写 brute force → 没有「外层 × 内层」的式子 → 没有能指着说「瓶颈在这」的东西 → **排序无处可推**。它不是灵光一现，是观察瓶颈的必然结果。

**自测点**：不看答案说出 brute force 是「什么 × 什么」，以及为什么该砍内层而不是外层

### 二刷 (8/10/2026) ❌ 补写 brute force，错的全在「变量此刻代表什么」和「循环何时退出」

```java
class Solution {
    public int hIndex(int[] citations) {
        int ans = 0;
        for(int h = 0; h <= citations.length; h++){
            int count = 0;
            for(int i = 0; i < citations.length; i++){
                if(citations[i] >= count) count++;
                // ❌① 阈值抓错 variable：应是 `>= h`。count 是正在累加的计数器，
                //    写成 `>= count` 等于让阈值边数边往上爬，语义完全变了
            }
            if(count >= h) return h;
            // ❌❌② 核心错误：升序枚举却命中就 return。h=0 时 count>=0 恒成立
            //    → 第一轮直接返回 0，外层 loop 等于没跑。`ans` 声明了从未被读取
        }
        return 0;
    }
}
```

改①之后我把②改成了 `return ans = h;` —— 仍然错。这是**先赋值再返回**，`return` 该退出照样退出。这个改法暴露的是误判：把「`ans` 没被用上」当成缺赋值，实际缺的是**别退出**。（另：把副作用藏进 return，面试中别写。）

**②的根因**：**枚举方向和退出方式必须配套。** 升序要的是「最后一个成立的 h」→ 只能 `ans = h` 记录、跑完再 return；降序要的是「第一个成立的 h」→ 才能立即 return。和 27 的「pointer 推进责任缺失」同族——condition 本身写对了，**没想清楚 loop 该在哪一刻结束**。

> **自检信号**：声明了却从未被读取的 variable，标记着「意图和实现脱节」的位置。本例的 `int ans = 0` 就是那个没被引爆的信号。

改完 brute force 再写 greedy 版，第三个 bug：

```java
if(citations[i] >= h) h++;
// ❌③ 应为 `> h`。判断发生在「加之前」，而这篇要满足的是「加之后」的阈值 h+1
//    反例 [0] → 返回 1（应为 0）；[1,1] → 返回 2（应为 1）
```

**③的根因**：`h` 在两段代码里是**两个不同的量**，处在不同的时间点上，所以一个带等号一个不带，**都对**：

|            | brute force            | 排序 greedy                      |
| ---------- | ---------------------- | -------------------------------- |
| `h` 的身份 | **候选阈值**，整轮静止 | **已接受的篇数**，边走边变       |
| 判断的含义 | 这篇够不够格计入阈值 h | 收下它后总数变 h+1，它够不够 h+1 |
| 正确符号   | `c >= h`               | `c > h`（即 `c >= h+1`）         |

①和③是同一个病：变量的角色在脑子里清楚，写到判断那一行时抓错了它**此刻**代表哪个量。

> **自检信号**：看到 `x++` 这类累加判断，先问「这个 variable 此刻是"加之前"还是"加之后"的值？」阈值要不要跟着 +1。注意「中文的至少 → 带等号」这条启发式**不是无条件的**，前提是比较两端处在同一时间点——前提一丢，启发式就骗人（同 ❌❌①）。

**自测点**：说出 brute force 的 `c >= h` 和 greedy 的 `c > h` 为什么一个带等号一个不带

### 第一步：把定义翻译成可判定的谓词

```
valid(h) ⟺ 引用数 ≥ h 的篇数 ≥ h        答案 = 最大的成立的 h
```

**先把「答案是什么」写成能对任意候选判真假的式子**，后面所有决策从它长出来。

### 第二步：brute force

h 的范围是 `[0, n]`（h 篇不可能超过总篇数），挨个试：

```java
int ans = 0;
for (int h = 0; h <= n; h++) {      // 闭区间 → <=
    int count = 0;                  // 声明在 loop 体内 = 自动重置
    for (int c : citations) {
        if (c >= h) count++;        // h 静止 → 带等号
    }
    if (count >= h) ans = h;        // 升序枚举 → 只记录，跑完再 return
}
return ans;
```

### 第三步：写出瓶颈的乘法式，逐个乘数看能不能砍

```
外层 h 从 0 到 n → n+1 次   ×   内层扫一遍数组 → O(n)   =  O(n²)
```

**嵌套 loop 的优化只有三个方向**：① 外层跑得少 ② 内层变便宜 ③ 换角度。没有第四个。

**先看内层**，问一句「各轮之间有没有重复劳动？」——h=3 数一遍、h=4 **扫的还是同一个数组** → 有重复 → 可预处理 → **砍得动**。（内层在「找 / 数 / 求区间和」几乎总能砍，工具是排序、HashMap、前缀和；只有各轮无可复用中间结果的独立计算砍不动。）

**再看外层**，条件是谓词单调，当场验证：「h 成立，h-1 一定也成立吗？」h=3 说明有 3 篇 ≥3；这 3 篇既然 ≥3 就一定 ≥2 → 够 2 篇 ✅ 单调成立，**也砍得动**。

**两个都能砍，算总账**：砍外层（二分答案）`log n × O(n)`，砍内层（排序）`n × O(1)`，都是 O(n log n)。**打平 → 选出错面小的**：二分要自己写 lo/hi/mid 收缩，边界容易错；排序是一行库函数，剩下是平凡的单层遍历。

> **两个别一起上**：排完序再二分是白搭——排序已付 O(n log n)，再省那 O(n) 不改总账，只增加出错机会。**砍到瓶颈不在那儿了就停手。**

### 第四步：砍内层 —— 把「数一遍」变成「查下标」

升序排好后，下标 `n-h` 上的就是第 h 大，它前面（含自己）恰好 h 个都 ≥ 它。

```java
class Solution {
    public int hIndex(int[] citations) {
        Arrays.sort(citations);                              // 升序 [0,1,3,5,6]
        int h = 0;
        for (int i = citations.length - 1; i >= 0; i--) {    // 倒序 = 从大到小
            if (citations[i] > h) h++;                       // h 是"加之前"的计数 → 不带等号
            else break;                                      // 优化，非正确性所需
        }
        return h;
    }
}
```

```
i=4 c=6  6>0 ✅ h=1     i=1 c=1  1>3 ❌ break
i=3 c=5  5>1 ✅ h=2     return 3
i=2 c=3  3>2 ✅ h=3
```

`break` 能成立是因为 h 单调不减、`citations[i]` 单调不增 → 一旦失败后面必然全失败，不 break 跑完结果一样。**先建立单调性，再决定能不能提前退出**——和上一步验证外层单调性是同一套动作。

**验证砍对了地方**：内层那个 `for (int c : citations)` 已经不见了，被 `citations[i]` 顶替。**看内层的 for 还在不在**，就知道砍的是哪个乘数。

### 复杂度分析

**Time: O(n log n)**：`Arrays.sort` 主导，之后单层遍历 O(n) 被盖住
**Space: O(log n)**：dual-pivot quicksort 是 in-place 的，但递归栈 O(log n)。说 O(1) 会被追问

对比 brute force O(n²)：快在把「每个候选都重新数一遍」换成「排一次序，之后 O(1) 查」。**预处理一次代替反复现算——这是砍内层的通用形态。**

### 沉淀

- **拿到暴力解的第一个动作是写出「外层次数 × 内层代价」**。没有这个式子就没有优化可谈（一刷全部的问题）。之后：先看内层有无重复劳动 → 砍不动再验外层单调性 → 都能砍就算总账、打平选出错面小的 → **砍完一个就停，别叠加**
- **优先看内层**：它是被外层放大的那个乘数，且"重复劳动"一眼能看出来，比验证单调性省脑子
- **枚举方向与退出方式配套**：升序找「最后一个成立的」→ 只能记录；降序找「第一个成立的」→ 才能立即 return。写 return 前先确认枚举方向
- **比较符号前先定位 variable 的时间点**：`x++` 前的判断里 x 是"加之前"的值，阈值要相应 +1。**同一个符号在不同上下文里对错相反**，别跨段套用
