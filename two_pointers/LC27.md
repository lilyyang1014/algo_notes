### 二刷 (7/23/2026) ❌ 改写 loop 时，无条件推进变成了条件推进

for 版本能 AC，改写成 while 就错了：

```java
while (fast >= 0 && fast < nums.length && slow < nums.length) {
    // ❌② 对正确实现而言条件冗余；slow 的限制掩盖了 fast 不推进的问题
    if (nums[fast] == val) {
        fast++;
    } else {
        nums[slow] = nums[fast];
        slow++;
        // ❌① 缺 fast++：反复复制同一个 element
        // slow 涨到 nums.length 后退出，返回错误个数
    }
}
```

**根因**：for 的 update statement 每轮执行；改写成 while 后只在一个 branch 推进 fast。这里应把 fast++ 放在所有 branches 之外。

### 四刷 (7/28/2026) ❌❌ LC26 旧版的 return 语义回流：slow 是 count 却 +1

loop body 全对，只错 return：

```java
// use fast to scan next valid element
// ❌② fast 扫描每个 element，是否保留由 if 判断

// [0, slow-1] is valid interval, k = slow
int slow = 0;
for (int fast = 0; fast < nums.length; fast++) {
    if (nums[fast] != val) {
        nums[slow] = nums[fast];
        slow++;
    }
}
return slow + 1; // ❌❌ slow 已是 count，+1 多算一个
```

**根因**：把 LC26 旧版「slow 表示最后一个确认位置，所以 +1」的修正动作搬了过来，却没有核对当前 slow 的含义。**return 应从当前有效区间推，不能背某题要不要 +1。**

**注释问题**：fast 负责扫描，if 负责判定；slow 指向 next write position，不是某个 element 本身。

> **自检信号**：写 return 前，先说出有效区间。当前版本为 `[0, slow)`，长度就是 slow；初始化、写入与推进顺序必须共同支持这个含义。

**历史自测点**：当前版本为什么从 slow=0 开始？退出时为什么直接 return slow？

### 七刷 (9/23/2026) ❌ 内层推进 fast 后，继续取值前没有检查范围

独立想到 two pointers：fast 扫描，slow 指向待写入位置。但写成「内层 while 跳过 val」：

```java
class Solution {
    public int removeElement(int[] nums, int val) {
        int slow = 0;

        for (int fast = 0; fast < nums.length; fast++) {
            while (nums[fast] == val) { // ❌ fast++ 后可能读取 nums[n]
                fast++;
            }
            nums[slow] = nums[fast]; // ❌ 也依赖 fast 仍然有效
            slow++;
        }
        return slow;
    }
}
```

**根因**：外层 condition 只保证进入本轮时 fast 有效；内层又改变了 fast，之前的检查不再能保护后续访问。

**反例 dry run**：`nums=[3], val=3`。fast=0 → 内层 fast++ 变成 1 → 再检查 while condition 时读取 nums[1] → 越界。

**两个容易误记的结论**：

- 不是 for 内禁止手动 fast++。原版找到有效 element 后会先复制，不能笼统说「多推进一次必然漏 element」；真正错误是推进后的访问没有保护。
- 只给内层补 `fast < nums.length` 也不够：退出时 fast 可能等于 n，后面的 `nums[fast]` 仍会越界。

**本轮收敛**：for 统一推进 fast；loop body 只判断当前 element 是否保留。`nums[fast] != val` 就写入并 slow++，否则跳过写入。

**自测点口答**：为什么 return slow 而不是 slow+1？答：「写入后 slow++，停留位置的 index 正好是保留的个数 k。」已理解；该问题已讲穿，不作为下次独立验收题。

修正代码由讲解提供，尚未提交独立重写版本，不记为一次写对。

### 正确写法

**fast 每轮前进一步；slow 只在保留一个 element 时前进一步。**

```java
class Solution {
    public int removeElement(int[] nums, int val) {
        int slow = 0;

        for (int fast = 0; fast < nums.length; fast++) {
            if (nums[fast] != val) {
                nums[slow] = nums[fast];
                slow++;
            }
        }
        return slow;
    }
}
```

等价的 while 版：fast++ 必须放在 branch 外。

```java
int slow = 0, fast = 0;

while (fast < nums.length) {
    if (nums[fast] != val) {
        nums[slow] = nums[fast];
        slow++;
    }
    fast++;
}
return slow;
```

### State 与 invariant

每轮开始时：

- fast：当前待检查的 index，`[0, fast)` 已处理。
- slow：下一个待写入的 index，同时也是已保留的个数。
- `[0, slow)`：已处理部分中所有不等于 val 的 elements，顺序保留。
- `0 <= slow <= fast`：写入不会覆盖尚未读取的后续数据。

退出时所有 elements 都处理完，有效区间长度为 slow，因此直接返回 slow。

### 复杂度分析

**Time: O(n)**：fast 扫描 n 个 elements，每轮 O(1)。
**Space: O(1)**：in-place，只使用两个 pointers。

对比每删一个 val 就把后续 elements 左移的 brute force，最坏 O(n²)：two pointers 避免反复搬动，每个 element 最多读一次、写一次。

### 沉淀

- **推进职责分清**：fast 每轮都动，由 for 管；slow 仅在写入后动，由 if 管。
- **移动可能让之前的范围检查失效**：loop 内改变 pointer 后，下一次读取前要重新确认合法性。
- **return 从有效区间推**：`[0, slow)` 的长度是 slow，不靠记忆补 +1。
- **冗余 condition 可能掩盖 bug**：二刷的 slow 限制没有修复推进遗漏，只把无限重复变成了错误返回。

> **自检信号**：每看到一次 pointer update，就检查下一次 array 访问由哪个 condition 保护。不要假设外层 loop 已经检查过，就能保护内层所有访问。

### Edge cases

- `[]` → 0：不进入 loop。
- `[3]`, val=3 → 0：全部删除，直接暴露七刷的越界。
- `[2]`, val=3 → 1：全部保留。
- `[2,3]`, val=3 → 1：末尾需要删除。
- `[3,2,3,4]`, val=3 → 2，前两格为 `[2,4]`：保留与删除交替。

### 引申：for vs while

**选更容易看清推进职责的写法，不是语法限制。**

- 固定扫描一个 array：for 能把初始化、condition、推进放在一起。
- pointer 的推进依赖 branch：while 往往更直观。
- 本题两种都能写；for 更容易避免遗漏无条件的 fast++。
- 改写 loop 时，要核对检查、取值和推进的执行顺序，而不只是替换关键字。

### 关联

- LC26：slow 的含义不同，return 也可能不同，不能直接搬用 +1。
- LC283：同样分开扫描与写入职责。
- LC88：pointer 变成 -1 或 n 本身不报错，继续拿它访问 array 才会越界。
