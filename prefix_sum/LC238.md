## 238. Product of Array Except Self

### 一刷 (8/15/2026) ⚠️ 结构建对，合并那一行下标归属滑掉

```java
int[] ans = new int[nums.length];
ans[0] = 1;                                  // ✅ 理由写对了：下标 0 左边没有元素，前缀积为 1
for(int i = 1; i < ans.length; i++){
    ans[i] = ans[i-1] * nums[i-1];           // ✅ 前缀积正确
}
int temp = 1;
for(int j = nums.length-2; j >= 0; j--){
    temp *= ans[j+1];                        // ❌① 应为 nums[j+1]
    ans[j] = ans[j+1] * temp;                // ❌② 应为 ans[j]
}
```

**整体结构是对的**：前缀积正向铺进 `ans`、后缀积用单变量反向累乘、原地合并、`ans[n-1]` 不动（它的前缀积已是全部元素、右边没东西，本身就是答案）。**两个错都在合并那一行。**

**❌①（手误）**：`temp` 攒的是**右边原始元素**的连乘，该乘 `nums[j+1]`。`ans[j+1]` 是已被加工过的前缀积，不是元素。口答确认「写的时候脑子里 `temp` 就是后缀积」——量的定义立住了，抓错了数组名。

**❌②（真正卡住的地方）**：答案是「j 左边所有元素的积 × j 右边所有元素的积」，两个因子**都归 j**——`ans[j]` 是 j 自己的前缀积，`temp` 是 j 自己的后缀积。写 `ans[j+1]` 取的是**右邻居的**前缀积，它比 `ans[j]` 多乘了一个 `nums[j]`，恰好把要排除的自己又乘了回来。

**❌② 还有第二层**：这个 loop 是**原地覆盖**的。`ans[j+1]` 在上一轮就已经被写成最终答案了，读它的时候它早就不是前缀积。

**dry run** `[1,2,3,4]`，前缀积 `[1,1,2,6]`，答案 `[24,12,8,6]`（①已修、②未修的版本）：

| j   | temp            | `ans[j+1] * temp`                     | 正确 `ans[j] * temp` |
| --- | --------------- | ------------------------------------- | -------------------- |
| 2   | ×nums[3]=4 → 4  | ans[3]=6 → **24** ❌                  | ans[2]=2 → **8** ✅  |
| 1   | ×nums[2]=3 → 12 | ans[2]=**24**（已被覆盖）→ **288** ❌ | ans[1]=1 → **12** ✅ |
| 0   | ×nums[1]=2 → 24 | ans[1]=**288** → **6912** ❌          | ans[0]=1 → **24** ✅ |

j=2 那轮只差一格；到 j=1，读到的 `ans[2]` 已是上一轮写进去的答案，错误被乘法一路放大。

> **自检信号**：**原地覆盖的循环里，凡是读邻居的那一行都要停一下**——问「这一格现在存的还是我以为的那个量吗？」。安全的写法是只读自己（`ans[j]`），要读邻居就说得出它此刻处于覆盖前还是覆盖后。

**归族**：同日第二次。早上 704 是 `left`（下标）与 `nums[left]`（值）被压成一个词，这次是 `nums[j+1]`（元素）与 `ans[j+1]`（前缀积）被压成一个词。**同一道缝：两个量共用一个下标位置，写那一行时只抓住了下标，没抓住它属于哪个数组。**（274 ①③、45 四刷、367、704 同族）

**自测点（8/23 已讲穿，作废）**：后缀积能不能改开第二个数组？——能，代价是 extra space 从 O(1) 变 O(n)。但**开了数组也修不好 ❌②**：`prefix[j+1]` 依然比 `prefix[j]` 多乘一个 `nums[j]`。开数组只消掉「读到被覆盖的值」那第二层，归属错的第一层原样还在。

### 二刷 (8/23/2026) ❌ 累积量 declare 在 loop 内，`last` 从没被更新过

一刷的两个错都没再犯（`nums[j+1]` 攒得对、两个因子都归 j）。我的代码：

```java
int last = 1;
for(int j = nums.length-2; j >= 0; j--){
    int suffix = last * nums[j+1];   // ❌ declare 在 loop 内 → 每轮重生；last 全程停在 1
    ans[j] = suffix * ans[j];        //    → suffix product 退化成单个 element nums[j+1]
}
```

**根因**：「后缀积」这个角色被劈成两个 variable，**谁都没承担跨 iteration 累积**——`last` 有名字有初值却没人更新它，`suffix` 每轮算完就随 iteration 销毁。把左边改成 `last` 即通过。

**症状很像「只差一点」**：`[1,2,3,4]` 得 `[2,3,8,6]`（期望 `[24,12,8,6]`）。**最右两格恒对**——`ans[n-1]` 不进这个 loop，`ans[n-2]` 的后缀本来就只有一个 element——越往左错得越狠，头两个 case 很容易看成小偏差。

**归族：LC80「count 该外置却内置」、LC380「三个 field 连着赋值写进 constructor → 成 local variable」，这是第三次。** LC80 笔记里那条沉淀原封不动适用，三次都没接到决策上。

**口答**：第二个数组那一问答得干净（能开、代价 O(n)），但「错的层数变没变」没接住；除法版那一问答成「total 不能为 0」——**炸的是 divisor 不是 total**，而这一条本篇「允许用除法」一节里早就写着。

**自测点（8/25 已讲穿，作废）**：第一趟若写成 `ans[i] = ans[i-1] * nums[i]`，后面要改什么？→ 见「引申二」。

### 核心思路（一句话）

**每个位置的答案 = 它的前缀积 × 它的后缀积。** 先正向一趟把前缀积铺进 `ans`，再反向一趟用单变量攒后缀积、就地乘上去——两趟 O(n)，除输出外不占额外空间。

### 代码

```java
class Solution {
    public int[] productExceptSelf(int[] nums) {
        int[] ans = new int[nums.length];
        ans[0] = 1;                              // 下标 0 左边没有元素，前缀积 = 1
        for (int i = 1; i < nums.length; i++) {
            ans[i] = ans[i-1] * nums[i-1];       // ans[i] = nums[0..i-1] 的积
        }
        int suffix = 1;                          // declare 在 loop 外：它要跨 iteration 活着
        for (int j = nums.length - 2; j >= 0; j--) {
            suffix *= nums[j+1];                 // 攒的是元素，且是累乘不是重算
            ans[j] = ans[j] * suffix;            // 自己的前缀 × 自己的后缀
        }
        return ans;
    }
}
```

`ans[n-1]` 不进第二个 loop：它的后缀积是 1，第一趟的结果已经是答案。

**两个边界值都是 1，不是 0**：乘法的单位元是 1。`new int[n]` 默认填 0，所以 `ans[0]` 必须手动置 1，否则整个前缀积链全是 0。

### 复杂度分析

**Time: O(n)**：两趟遍历。
**Space: O(1)**（不计输出数组）：只多一个 `suffix`。

对比：开两个数组分别存前后缀再合并，思路更直白但要 O(n) 额外空间；朴素做法对每个位置重新乘一遍其余元素是 O(n²)。

### 引申一：如果允许用除法

写法是 `ans[i] = total / nums[i]`——**出事的是 divisor**，`nums[i] == 0` 时抛 `ArithmeticException: / by zero`。`total` 为 0 完全合法（`0 / 5` 就是 0），别把被除数和除数抓成一个词。

要写对得先统计 0 的个数，分三支：

- 没有 0：直接除
- 恰好一个 0（位置 k）：`ans[k]` = 其余元素之积，**其余位置全是 0**
- 两个及以上 0：整个 ans 全是 0

比前后缀两趟麻烦，所以题目禁除法其实并不是主要难点。

### 引申二：`ans[i]` 的定义，决定它该乘到哪一格为止

第一趟若写成 `ans[i] = ans[i-1] * nums[i]`，`ans[i]` 存的就是 `nums[0..i]` 的积——**比正确的 prefix 多乘了 `nums[i]` 自己**。

下游要跟着改，但**这条路是死的**：合并那一行得写成 `ans[j] * suffix / nums[j]`，题目禁除法。也不能靠第二趟少乘一格来抵消——`suffix` 攒的是 j 右边的元素，跟 j 自己无关，两边各管各的一侧，谁也补不了谁的账。

所以唯一的修法是把定义拧回来：`ans[i]` 必须是「**i 左边（不含 i）所有元素的积**」，而 `ans[0] = 1` 正是这个定义在 i=0 时的取值（左边没有元素 → 空积 = 1）。定义、初值、递推式三者是一套，动一个另外两个必须跟着核。

**这一条会迁移**：所有 prefix 型的题都有同一个岔路口——`prefix[i]` 到底含不含 `i` 自己。前缀和里它决定区间查询写 `prefix[r+1] - prefix[l]` 还是 `prefix[r] - prefix[l-1]`，是同一件事的加法版。**先钉死定义，再写递推。**

### 沉淀

- **前后缀分解**：形如「除自己以外的全部聚合」的题，标准拆法都是 `左边的聚合 ⊕ 右边的聚合`，两趟扫描。乘法如此，加法、最大值同理。
- **跨 iteration 的累积量 declare 在 loop 外**：声明位置决定生命周期。写在 loop 里的直接症状是「累积值永远停在初值」或「依赖累积的 condition 永不触发」——和 LC80 的 `count`、LC380 的 field 是同一条。
- **两个因子必须归同一个下标**：`ans[j]` 配 `suffix`，都是 j 自己的。合并那一行读到 `j+1` 就该警觉。
- **动了递推式就是动了定义**（见引申二）：改完先重读定义，再核初值和下游，别等 dry run 报警。
- **原地覆盖时，邻居不再是原来的量**（见一刷的自检信号）。
- **边界值取的是运算的单位元**：乘法 1、加法 0。默认值 0 对乘法是毒药。

### Interview pitch (练口述)

> "Each answer is the product of everything to the left times everything to the right, so I compute it in two passes. The first pass fills the output array with prefix products — ans[i] is the product of nums[0..i-1], with ans[0] set to 1 since nothing is to its left. The second pass walks backwards with a single running suffix variable, multiplying it into each slot in place. That's O(n) time and O(1) extra space beyond the output. Two details matter: the suffix variable lives outside the loop because it has to accumulate across iterations, and both factors have to belong to the same index — the prefix already sitting in ans[j], and the suffix I've accumulated for j."
