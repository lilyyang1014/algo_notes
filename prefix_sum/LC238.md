## 380. Insert Delete GetRandom O(1)

Date: 8/10/2026, 8/11/2026
Difficulty: Medium
Tags: hash map, dynamic array, swap-and-pop, design

![Two containers side by side: a List holding values by index and a HashMap from value to its index; remove() overwrites the target slot with the last element, pops the tail, and updates the map entry for the moved element](assets/380.png)

### 一刷 (8/10/2026) ❌ 没思路（**读题解，非独立解出**）

**真正的坎**：三个操作要的能力互斥——`getRandom` 要「按下标随机取」（只有 array/list 有），`containsKey` 要「按值查」（只有 map 有）→ 必须同时维护两个容器，map 存 `value → list 下标`。这一层没建立，remove 的填坑技巧就无从谈起。

**唯一的实际 bug（compile error）**：三个 field 连着 `= new ...()` 整行写进了 constructor 里 → 成了 local variable，其他方法找不到声明。

> **自检信号**：带类型前缀的那一行就是**声明**；声明写在哪个花括号里，variable 就活在哪个花括号里。design 题第一步先把 field 列在类体，constructor 只负责 new。

### 二刷 (8/11/2026) ❌ swap-and-pop 只写了一半（**真正的 day 0**）

```java
public boolean remove(int val) {
    if(!map.containsKey(val)) return false;
    int idx = map.get(val);
    int last = list.get(list.size()-1);
    list.set(list.size()-1, val);   // ❌❌ 核心错：写向一个马上要删的格子，
                                    //    真正需要的 list.set(idx, last) 缺失
    list.remove(list.size()-1);
    map.put(last, idx);             // 宣称 last 住在 idx——list 那边从没兑现
    map.remove(val);                // ❌ 注释写成 "remove the last element"，实际删的是 val 的 key
    return true;
}
```

**❌❌ 的根因**：心智模型是对的（「把 val 换到末尾再删末尾」），但以为 swap 需要两次赋值，只写了其中一次。**实际只需要一次**——末尾那格马上要删，往里写什么都是白写。所以漏的不是两次里的一次，**是唯一那次**。后果：idx 位置的 val 原封不动还在，last 反而从 list 里消失。

**反例 dry run**：`list=[10,20,30]`, `map={10:0,20:1,30:2}`，`remove(10)`

| 行           | list         | map                |
| ------------ | ------------ | ------------------ |
| `set(2,10)`  | `[10,20,10]` | —                  |
| `remove(2)`  | `[10,20]`    | —                  |
| `put(30,0)`  | —            | `{10:0,20:1,30:0}` |
| `remove(10)` | —            | `{20:1,30:0}`      |

该删的 10 还在、没让删的 30 没了，且 map 说 `30→0` 而 `list[0]=10`。**静默错误**，且会滚雪球：下次 `remove(30)` 拿 idx=0 继续搬错。

**自测点**：`getRandom` 的等概率到底靠什么保证？若 remove 时不填坑、直接 `list.remove(idx)`，等概率还成立吗？三个方法的复杂度各变成什么？

### 核心思路（一句话）

**两个容器互补：list 提供 O(1) 按下标随机取，map 提供 O(1) 按值查下标；删除时用「末尾元素填坑 + 删末尾」把 O(n) 的中间删除降成 O(1)，代价是放弃顺序（本题不需要）。**

### 代码

```java
class RandomizedSet {
    Map<Integer, Integer> map = new HashMap<>();   // value → 它在 list 中的下标
    List<Integer> list = new ArrayList<>();
    Random random = new Random();                  // 当 field 造一次，不要每次 new

    public RandomizedSet() {}

    public boolean insert(int val) {
        if (map.containsKey(val)) return false;
        list.add(val);
        map.put(val, list.size() - 1);   // 必须在 add 之后：下标由 add 之后的长度决定
        return true;
    }

    public boolean remove(int val) {
        if (!map.containsKey(val)) return false;
        int idx  = map.get(val);
        int last = list.get(list.size() - 1);
        list.set(idx, last);             // 末尾值填进坑（此刻 last 有两份拷贝）
        list.remove(list.size() - 1);    // 删末尾 → O(1)，后面没有 element 要搬
        map.put(last, idx);              // 先更新幸存者
        map.remove(val);                 // 再删死者，顺序不可换
        return true;
    }

    public int getRandom() {
        return list.get(random.nextInt(list.size()));   // nextInt(n) 是 [0, n)
    }
}
```

**不变量**：任意时刻，对 list 里的每个 element，`map.get(element)` 必须等于它在 list 中的真实下标。任何一次移动 element 的操作，都要在同一步里恢复这条不变量。

**map 两行顺序不可换**：`val` 恰好是末尾 element 时 `last == val`，两行在**同一个 key** 上做相反操作，后写的赢。`remove` 是最终意图，必须在后。写反了 → `[10,20]` 删 20 会把 key 20 又塞回去，`insert(20)` 从此永远 return false，再 `remove(20)` 直接 IndexOutOfBoundsException。

### 复杂度分析

**Time**：insert / remove / getRandom 均摊 **O(1)**。remove 的 O(1) 完全建立在「删末尾」上
**Space: O(n)**：两个容器各存一份 n 个 element

对比只用 list 的朴素做法：`contains` O(n)、`remove(Object)` O(n)。map 买来的是「按值查」，list 买来的是「按下标随机取」，两个能力单独任一容器都给不全。

### 沉淀

- **两容器结构，任何一次搬运必须两边都改**：写完 map 的更新，回头问一句「map 说的位置，list 上真的是那个值吗」。这次是**同一个事实在两个容器里只写了一处**——和 LC274/LC45 的「同一个名字指两个量」是一族的镜像，共同点都是脑子里模型对、落到某一行只兑现了一半。
- **「更新 A + 删除 B」成对操作，先问 A 和 B 会不会是同一个东西**：可能重合就把删除放最后。
- **`list.remove(i)` 的复杂度取决于 i**：删中间 O(n)（后面整体左移），删末尾 O(1)。要 O(1) 删任意 element 的标准技巧就是填坑 + 删末尾，前提是容器不要求有序。
- **design 题的解法从「把需求翻译成能力」推出来**：先列每个方法要什么能力，再看哪个容器提供，缺就补一个容器。不是记模板。
- **`nextInt(n)` 是 `[0, n)`**，正好对应 list 的合法下标范围，不需要 `-1`。

### Interview pitch (练口述)

> "The constraint is O(1) for all three operations, and no single container gives me that. A list gives O(1) random access by index but O(n) lookup by value; a hash map gives O(1) lookup by value but no indexable ordering for random selection. So I keep both: the list holds the values, and the map goes from value to its index in the list. Insert appends and records the new index. Remove is the interesting one — deleting from the middle of a list is O(n) because everything shifts, so instead I overwrite the target slot with the last element, pop the tail, and update the moved element's index in the map. That's O(1), and I lose ordering, which this problem doesn't need. One edge case: if the element being removed is already the last one, the map update and the map delete touch the same key, so the delete has to come second."
